# Install a local Fortress development build

The portable package contains the native Fortress CLI, an independently installable VSIX, the standalone Python assurance verifier, an offline copy of the registered Standard and schema assets, and the locked workspace dependency inventory. The schemas and protocol documentation let local clients consume the existing public wire formats. The dependency inventory describes the workspace lock and carries no vulnerability-assurance result.

## Select the package

| Target | Format | Runtime |
| --- | --- | --- |
| Windows x64 | ZIP with `bin/fortress.exe` | Native Windows x64, Universal CRT, and the Microsoft Visual C++ v14 x64 Redistributable |
| Linux x64 | ZIP with `bin/fortress` | Native x86-64 Linux with the GNU C runtime and the libraries required by the build |
| macOS arm64 | Proposed | No qualified package or format reader |

Use the exact target and runtime evidence accompanying the package. A development build uses product version `0.1.0`. Product versions, Standard editions, and protocol versions have separate identities. The packaged extension uses native query versions 1–5 according to negotiated capabilities. The local MCP server supports MCP `2025-11-25` and `2025-06-18`. The desktop qualification target is VS Code Desktop 1.147.0 on Windows and Linux x64.

## Verify and install

Obtain `install.py`, `manifest.json`, the ZIP, and the manifest SHA-256 through a trusted local channel. Independently check the expected installer SHA-256 before running it. Pass the independently obtained manifest SHA-256 to the installer. The manifest binds the raw ZIP and each installed file. SHA-256 checks validate content integrity. Issuer authenticity and public-release authorization remain unverified for these development artifacts.

On Linux, use a private user-owned application directory and Python 3.11 or later.

```sh
python3 -I -B install.py verify fortress-0.1.0-linux-x64.zip manifest.json --manifest-sha256 "$MANIFEST_SHA256"
python3 -I -B install.py install fortress-0.1.0-linux-x64.zip manifest.json "$HOME/.local/fortress" --manifest-sha256 "$MANIFEST_SHA256"
```

On Windows, use a private directory under your user profile. The CLI imports `VCRUNTIME140.dll`. Install the supported x64 runtime separately if it is missing, then confirm that the installed CLI launches with `--version`. [Microsoft Visual C++ Redistributable](https://learn.microsoft.com/en-us/cpp/windows/latest-supported-vc-redist/)

```powershell
python -I -B .\install.py verify .\fortress-0.1.0-windows-x64.zip .\manifest.json --manifest-sha256 $ManifestSha256
python -I -B .\install.py install .\fortress-0.1.0-windows-x64.zip .\manifest.json (Join-Path $env:LOCALAPPDATA 'Fortress') --manifest-sha256 $ManifestSha256
```

The reply supplies the exact installed slot. Invoke its `bin/fortress` or `bin/fortress.exe` by absolute path. Optionally add that verified `bin` directory to your user `PATH`. Check which command the shell resolves with `command -v fortress` or `Get-Command fortress` before use. Installation leaves `PATH`, editor settings, repositories, and project governance unchanged. Each installed application slot is separate from repositories, certificate materializations, and migration recovery storage.

## Use the installed CLI

Run `fortress --version`, `fortress status /absolute/project`, and `fortress doctor /absolute/project` from any directory. `fortress query modules /absolute/project` lists supported architectural Modules. Use `fortress explain <identity> /absolute/project` with a reference from that project. Saved evidence keeps its original source bindings. A missing or stale selection has no current assurance meaning. Ordinary inspection and static analysis use the packaged native executable without Rust, Cargo, Node, or Python. Registered native test execution for certification requires the respective external toolchain. Offline `fortress bundle verify` uses a trusted Python 3.11+ executable. Set `FORTRESS_VERIFIER_PYTHON` to its absolute path outside the working and bundle trees. The separately usable `share/verify_bundle.py` also runs offline with standard-library Python. Its result distinguishes integrity from execution, freshness, and authenticity.

In VS Code Desktop use **Extensions → Install from VSIX** on the manifest-verified `editor/fortress-development.vsix`. Set `fortress.executable` in User Settings to the absolute installed CLI path outside candidate repositories. The extension respects workspace trust. Remove it through the Extensions view or with `code --uninstall-extension fortress-development.fortress-inspection`. The CLI installation is independent of that editor action.

Register the verified executable and its argument array in the trusted local MCP client configuration. The Codex stdio entry uses this format.

```toml
[mcp_servers.fortress]
command = "/absolute/install/bin/fortress"
args = ["serve", "--mcp", "/absolute/project"]
startup_timeout_sec = 120
```

Use absolute native paths and the platform executable name. Candidate preparation additionally requires an explicitly selected external storage directory. MCP does not grant permission to write. GitHub production enforcement remains `UNVERIFIED`.

When applying a separately reviewed project migration, select a private external directory on the project’s volume using the established storage configuration. If the operating system puts temporary files on another volume, set `FORTRESS_EXECUTION_STORAGE_DIR` for commands that use default migration storage.

## Replace or remove a build

Reinstalling an identical manifest rechecks the archive and the installed inventory. To replace a qualified build of the same product version and platform, pass `--replace OLD_SLOT OLD_MANIFEST_SHA256` to `install`. The new build receives a separate slot. Switch your trusted client settings or `PATH` to it after verification. The previous version remains available until explicit removal. Other version relationships require a qualified compatibility declaration. Application replacement does not upgrade any project Standard or schema.

Use `python -I -B install.py remove /absolute/install-root SLOT --manifest-sha256 SHA256` to remove the exact application files. Close running consumers first. Leave user-owned files beside application slots. The installer refuses changed files, linked destinations, and unexpected entries. An interrupted install never exposes the incomplete slot. Repeat the verified installation if the final slot is absent. An interrupted removal can resume with the same slot and manifest identity, while the retained tombstone manifest is still present. Preserve uncertain staging or interrupted state for review. These operations use a private directory and a cooperating installer lock. They do not establish guarantees against a privileged process that can rewrite the private store, or arbitrary power loss.

## Optional Python lexical inspection

The verified installed slot includes the compile-only worker at `share/fortress/workers/python_lexical_worker.py`.
Use it with a trusted CPython 3.12 or 3.13 installation outside the project. An independent host registers the absolute interpreter and installed worker paths, exact interpreter digest, exact runtime descriptor and grammar. Select the original repository and a single repository-relative Python file explicitly through `fortress source-artifacts --observe-python PROJECT HOST_REGISTRATION SOURCE_PATH lexical`.
The registration schema is available in the installed CLI schema inventory. The observation has compile-only scope and retains unsupported import, call, effect and execution behavior.

## Optional Python scalar inspection

The installed executable has both verified worker assets one directory above
its bin directory, under share/fortress/workers. Select the absolute paths to
python_scalar_worker.py and its sibling python_lexical_worker.py in the trusted
host registration. The CLI verifies the exact installed bytes. Bring an
independently pinned CPython 3.12 or 3.13 installation on Windows x64 or Linux
x64. The installed slot supplies the worker and the separate scalar registration
schema.

Use fortress source-artifacts --observe-python-scalar PROJECT HOST_REGISTRATION.
The registration selects the exact subject file hash, function name and
independently established exact bool parameter names. The optional output bound
applies only under those assumptions. The result retains unresolved runtime
argument types and an explicit unavailability status when scope is incomplete.

## Optional Go native inspection

A package may contain prebuilt Go workers in its bin directory. Check
the verified manifest's build.native_go attachment for the exact worker paths,
protocols, executable digests, original source and SDK identity. Installation
copies each approved worker with executable permissions. Use the current
installer supplied with that package. These workers run without a Go SDK on the
installed machine.

Keep each host registration outside the observed project. Set its executable
to the absolute installed path after independently selecting the worker and
reviewing its digest. Use the exact host and compiler version in the worker
attachment. A package digest verifies package contents. Host trust remains an
independent selection, and a package does not create a registration or run a
worker on installation.

Select the asset for the command and use its corresponding independently
configured external registration.

| Worker edition | CLI command | Additional worker modes |
| --- | --- | --- |
| v1 | psm --observe-go | legacy observation |
| v3 | psm --observe-go-module | legacy observation and v2 build selection |
| body-v1 | psm --observe-go-body | legacy observation |
| tests-v1 | psm --observe-go-tests | legacy observation and v2 build selection |

For psm --observe-go-build use the combined v3 worker with a v2 registration.
Body and test declarations have distinct worker executables and registration
schemas. The body worker reports bounded source observations. Test declaration
inspection does not execute project tests or supply verification evidence.
The schemas are part of the installed schema inventory. The development
targets are Windows x64 with go1.22.12 and Linux x64 with go1.22.2.

To opt in at build time, append the following to the existing exact-source build
command. Supply the independently pinned, unprefixed lowercase SDK inventory
SHA-256 for the selected absolute installation.

    --go-sdk SDK_ROOT --go-sdk-sha256 SDK_SHA256 --go-worker v1 --go-worker v3 --go-worker body-v1 --go-worker tests-v1

The preparation checks the native SDK command, tool programs and standard
sources before and after staging. It builds only the fixed worker sources
with the recorded flags and disables fetching. The requested full package
build also uses offline Cargo and npm caches. Missing dependencies or a
different SDK inventory fail explicitly. The older v1 package reader can
verify new package member bytes, while the supplied current installer grants
executable permissions to the recognized additional worker files.
