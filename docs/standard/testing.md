# 18 — Testing, Coverage, Conformance, and Quality Evidence

**Status:** Normative testing and conformance standard
**Authority class:** Quality and trust

## Principle

Passing tests are necessary but do not by themselves prove a Fortress-quality codebase.

Fortress combines requirement traceability, structural coverage, conformance, mutation, property/fuzz evidence, architecture tests, and documentation/source checks according to applicability and risk.

## Requirement-first testing

Every externally meaningful product feature must be contracted.

Every normative requirement must have explicit test/evidence mapping.

The primary coverage claims are:

- 100% active feature coverage;
- 100% mandatory normative requirement coverage.

A single test cannot create false whole-feature coverage.

## Test identity

Every product-behavior test has a stable unique ID referencing the requirement it proves.

Example:

`T-PF-ARCH-0017-R01-001`

Fortress rejects duplicate IDs, invalid references, orphan normative requirements, and unclassified product behavior tests.

## Test classes

Feature/risk contracts may require:

- unit;
- integration;
- end-to-end;
- positive;
- negative;
- boundary;
- conformance;
- cross-platform;
- property-based;
- fuzz;
- mutation;
- performance;
- security;
- migration;
- differential.

## Structural code coverage

Contract/requirement coverage is primary.

Structural code coverage remains a secondary hard gate.

The default target for hand-authored production logic SHOULD be 100% reachable statement coverage and 100% reachable branch coverage, with explicit governed exemptions for genuinely unreachable or platform-exclusive paths.

Generated code is measured separately.

Fortress must not encourage pathological tests solely to inflate metrics.

## Mutation testing

Tests should demonstrate an ability to detect meaningful defects.

Changed-feature mutation testing may gate development integration.

Full mutation analysis may gate release for profiles where practical.

Meaningful surviving mutants must be killed or explicitly classified with evidence as equivalent/non-actionable.

## Property testing and fuzzing

Parsers, canonicalizers, serializers, policy engines, protocol boundaries, and state machines should use property/fuzz testing when risk warrants it.

Discovered fuzz failures become persistent regression fixtures with test identities where applicable.

## Cross-language semantic conformance

For multilingual products, all language surfaces consume the same normative contracts and specification-authored conformance corpus.

Expected golden output MUST NOT be generated by one implementation and then treated as authority for others.

Suitable randomized inputs may be executed across language surfaces and normalized to canonical semantic artifacts for differential testing.

## Fortress rule conformance

Fortress itself requires a separate conformance corpus of miniature repositories.

Every rule should include appropriate:

- passing fixture;
- failing fixture;
- boundary fixture;
- expected canonical diagnostic;
- exemption case;
- conflict case.

## Analyzer conformance

Language analyzers claiming a capability must pass analyzer-protocol conformance proving deterministic extraction and canonical representation.

## Architecture fitness tests

Machine-readable architecture rules are tests too.

Fortress should verify:

- allowed dependency direction;
- file placement;
- ownership;
- forbidden cycles;
- public/private boundaries;
- generated-artifact authority;
- command/pipeline graph integrity.

## Reproducibility tests

Generators and derived evidence must reproduce deterministically.

A verification pass should regenerate applicable outputs and require a clean diff.

## Test source authority

Implementation tests provide evidence but do not define normative product semantics.

If an implementation test conflicts with a ratified contract/specification, the test is wrong unless the higher authority is changed through governance.

## Risk-proportional depth

Fortress is intentionally strict but does not require every low-risk pure helper to undergo the same fuzz campaign as an untrusted-input parser.

The contract specifies applicable evidence obligations.

## Performance evidence

Performance rules must use explicit thresholds, environments, and datasets when they are certification requirements.

Unstable microbenchmark noise should not create false hard gates.

## Test execution and certification cache

Expensive suites should be partitionable into certification units and resumable/shardable jobs where possible.

Content-addressed certification allows unchanged proof to remain valid.

## Goal

Fortress testing proves not only that code executes successfully, but that every promised behavior has explicit evidence and the test system is strong enough to detect meaningful violations of those promises.
