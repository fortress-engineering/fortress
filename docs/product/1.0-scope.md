# 22 — Fortress 1.0 Scope and Product Boundary

**Status:** Normative 1.0 release boundary
**Authority class:** Release scope

## Purpose

Fortress 1.0 must be broad enough to prove the complete product thesis without becoming an endless attempt to support every language, framework, cloud, CI provider, or development tool before first release.

The stable 1.0 boundary is therefore defined by **complete architecture plus bounded first-party coverage**.

## 1.0 defining capabilities

Fortress 1.0 MUST include a coherent implementation of the following product pillars.

### Standard engine

- Fortress Engineering Standard 1.0.0;
- immutable standard bundle and digest;
- core rule model;
- archetype/capability composition;
- project extensions;
- exemption model;
- standard upgrade planning.

### Project model

- stable entities for components, features, requirements, files/symbol ownership, tests, docs, commands, pipelines, invariants, changes, and certifications;
- declared/observed distinction;
- graph queries;
- architecture zones and dependency contracts.

### Auditing

- repository inventory;
- normalized findings;
- strict source/tool integration for first-party languages;
- architecture and contract drift detection;
- docs and generated-artifact validation;
- public API/ownership capabilities sufficient for first adopters.

### First-party deep languages

1.0 SHOULD provide strong built-in deep analyzer/tool support for:

- Rust;
- TypeScript/JavaScript;
- Python.

Other languages receive universal repository analysis and may use extension analyzers.

Unsupported required semantic analysis blocks full certification rather than silently passing.

### Certification

- certification DAG;
- PASS/FAIL/STALE/MISSING/INVALID states;
- content-addressed fingerprints;
- `fortress affected`;
- `fortress certify --affected`;
- `fortress certify --all`;
- rebaseline;
- canonical certification artifacts;
- attestation verification;
- cheap-CI evidence validation.

### Command/runtime control plane

- project command registry;
- typed parameters;
- local command execution;
- async job submission;
- status/help/explain;
- artifact/provenance capture.

### Job system

- persistent local job state;
- background execution;
- logs/events;
- progress models;
- cancel;
- restart/recovery;
- checkpoint/shard resumption where command semantics support it.

### Pipeline governance

- canonical pipeline/job contracts;
- local pipeline execution where compatible;
- GitHub Actions provider integration as first provider;
- provider run/status/log/cancel integration;
- pipeline certification prerequisites;
- audit of provider workflow alignment.

### Temporal governance

- change intent;
- planned change contracts;
- scope drift detection;
- executed change records;
- project invariants;
- transition contracts;
- archived ledger;
- release records.

### Onboarding governance

- forensic scan;
- observed/inferred/ratified states;
- archetype/component hypotheses;
- target-model workflow;
- staged convergence graph;
- LOCKED/PROVISIONAL/ACTIVE/SATISFIED findings;
- migration baseline;
- ratchet;
- dependency-valid next migration unit;
- historical violation tracking.

### Self-application

- Fortress repository governed by its own strongest implemented standard;
- full pre-1.0 migration of Fortress to Standard 1.0 expectations;
- credible Fortress self-certification for release.

## Source-quality strictness in 1.0

Fortress 1.0 should demonstrate hard-gated integration for:

- formatting;
- strict typing/static analysis;
- naming;
- source documentation;
- complexity;
- repository hygiene;
- dependency governance;
- test/requirement mapping.

It should synthesize or validate compatible tool configuration rather than leave conflicts unresolved.

## Rule corpus

Every mandatory Fortress 1.0 rule must have conformance fixtures sufficient to demonstrate correct PASS/FAIL behavior and diagnostic stability.

## Explicitly deferred from 1.0

The following are not required for stable 1.0 unless implementation proves low-risk and mature:

- first-party deep analyzers for every language;
- hosted Fortress SaaS/control plane;
- every CI/CD provider;
- every cloud provider;
- a public extension marketplace;
- organization-wide multi-repository certification as a fully mature feature;
- full OS-level sandboxing for all third-party extensions;
- autonomous architecture decisions without human ratification during ambiguous onboarding;
- AI model hosting/generation inside Fortress itself.

The architecture must remain extensible to these.

## First external proving ground

After Fortress 1.0 is developed and self-certified, `strling-lang/strling` is the intended first demanding external adoption/migration proving ground.

STRling MUST NOT dictate Fortress's foundational architecture before Fortress is independently coherent.

## Success criteria

Fortress 1.0 succeeds when it can:

1. initialize a new governed repository;
2. audit a non-Fortress repository;
3. produce a meaningful onboarding convergence plan;
4. enforce architecture/contracts/source/documentation/testing rules;
5. execute project commands and long-running jobs;
6. compute precise affected certification;
7. persist and verify trusted certification evidence;
8. govern a change through the temporal ledger;
9. manage a GitHub-oriented pipeline;
10. certify Fortress itself.

## Product discipline

The 1.0 implementation must prefer complete trustworthy semantics over a broad list of shallow integrations.

The standard is harsh; the implementation must be equally honest about what it can prove.
