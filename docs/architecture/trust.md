# 19 — Security, Trust, Provenance, and Attestation Model

**Status:** Normative security and trust architecture
**Authority class:** Quality and trust

## Scope

Fortress is not primarily a cybersecurity product, but its certification claims are only useful if evidence, analyzers, tools, extensions, and remote results have a defensible trust model.

Security is therefore part of Fortress certification integrity.

## Threat assumptions

Fortress must assume that any of the following may be malformed, stale, misleading, compromised, or malicious:

- repository source;
- user-authored certification JSON;
- third-party analyzers/extensions;
- external tool output;
- remote CI responses;
- downloaded standard bundles;
- package metadata;
- generated artifacts.

## Standard bundle integrity

Released Fortress Standard editions are immutable and digest-addressed.

A project lock records the exact standard version and digest.

Fortress must verify the bundle before certification.

Signed release metadata is preferred for protected workflows.

## Certification attestations

A PASS field is not trusted evidence.

Protected certification must be able to bind cryptographically:

- certification definition;
- standard digest;
- project/input fingerprint;
- dependency manifest digest;
- Fortress/toolchain versions;
- result;
- evidence digests;
- signer/provenance.

## Initial cryptographic model

The implementation should use a modern, reviewed signing scheme and a versioned attestation format.

The exact algorithm may be selected during implementation architecture, but the protocol must support algorithm agility and MUST NOT encode ad hoc unversioned signature blobs.

## Trust levels

Recommended certification trust levels:

### Untrusted Local

Evidence generated by an arbitrary local environment. Useful for development feedback but not sufficient for protected release claims.

### Trusted Development

Evidence produced by an approved maintainer/self-hosted identity or controlled environment.

### Release Grade

Evidence produced under the complete release profile with required provenance and signatures.

## Identity separation

For repositories whose protected `main` branch must only be updated by an owner, autonomous agents should ideally use a separate GitHub identity/App/bot whose permissions cannot update `main`.

Procedural prompts alone do not create identity separation when agents authenticate as the owner.

## Extension trust

Third-party analyzers and adapters have explicit trust state.

Untrusted extensions may support exploratory audit but cannot automatically satisfy protected certification.

Certified extensions pass the applicable extension/analyzer conformance suite and provenance policy.

## Process isolation

Fortress should prefer bounded execution for untrusted analyzers/tools where practical.

Full sandboxing is not necessarily a bootstrap prerequisite, but the architecture must not require arbitrary extensions to execute inside unrestricted Fortress core memory.

## Secret handling

Fortress may model secret requirements but MUST NOT store plaintext secrets in versioned project contracts or certification artifacts.

Runtime secret values are resolved through environment/provider-specific secure mechanisms.

Logs and evidence must avoid accidental secret capture.

## Supply-chain policy

Fortress should support dependency governance including:

- explicit dependency purpose;
- version policy;
- license classification;
- vulnerability evidence;
- direct/transitive identity;
- lockfiles;
- package provenance where available.

Adding an external dependency is an engineering-model change, not merely an import.

## Remote CI evidence

Provider success state alone is insufficient for release-grade trust.

Fortress should bind remote job identity, exact inputs/artifact digests, relevant workflow definition, and returned evidence into the certification graph.

## Tamper detection

Committed certification evidence is verified against content digests and signatures.

Manual modification must make evidence INVALID rather than silently changing the certification result.

## Revocation and compromise

The trust model should leave room for revoking compromised signing identities or invalidating affected attestations without mutating historical standard meaning.

## Security certification as one capability

Fortress can integrate deep security scanners and secure-development policies as certification units.

Those tools are part of the broader engineering standard; they do not redefine Fortress as a perimeter-security product.

## Goal

A Fortress certification should be trustworthy because the evidence chain is bound to exact inputs and authorized execution, not because the repository contains a green badge file.
